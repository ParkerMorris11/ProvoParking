# KR 2b: time from opening to timer start

The Sprint 2 card defines the KR as the average time from opening the app to starting a parking timer, target at most 15 minutes. For each account-backed `parking_session`, use the most recent same-user visit at or before its start and no more than one hour earlier. Unfinished and unmatched visits are excluded. Starting a timer is a proxy; it does not verify that a vehicle is parked.

## Design and privacy

`app_visit` is additive. It stores a random visit ID, a hash of a random capability, server opening time, optional account owner, and a separate private link for each successful timer start. It stores no name, email, location, or car note. Account-linked visits are deleted when their Auth user is deleted; a session link is deleted if its parking session is deleted. Raw rows have RLS and no browser-role table grants. The browser can only call narrowly scoped invoker RPCs; their privileged helpers live in a dedicated unexposed schema. Account completion verifies `auth.uid()` against the owner of the real `parking_session` and selects the latest bound visit in the preceding hour. A later account bind repairs eligible session links if a newer tab opened before the timer start but bound afterward. Guest completion requires the visit capability and reports a local session ID and timestamp: it is **client-reported**, not server-verified. A capability is generated independently per tab and kept in sessionStorage, not a URL. Never log or share it.

The server stamps openings. Session storage preserves the original visit through reload and navigation within a tab, so refresh does not restart the clock. Tabs opened independently have independent visits. Browsers that duplicate a tab can clone sessionStorage; such a clone shares the visit capability; if the tabs bind different accounts, the denied tab creates a new visit at sign-in. Refreshing after an hour starts a new visit; a page left open without refreshing keeps its original opening time, so starts more than one hour later are excluded. A failed timer start never completes a visit. Each successful start is queued independently before navigation and retries after page reload or an online event for up to 24 hours; account-specific entries wait until that account is signed in again; server calls are idempotent. The account path uses the session row’s start time. The current legacy timer grants authenticated users direct insert access, so a malicious client can forge that timestamp; it is database-backed, not tamper-proof. The standalone local flow records a guest completion only for a non-sample location; its current default is a labeled sample, so those demonstrations do not affect the KR. Offline/no storage/no configuration must not block the timer, but visits may be lost. If the server first receives an opening only after the timer started, it cannot reconstruct that start and excludes it. Client clock skew can exclude or distort guest results. Guest reports cannot prove a timer was started and should be considered separately from the official account KR.

`supabase/queries/kr-2b.sql` is a database-admin query returning counts and average minutes separately for account-backed links and client-reported guests; it excludes unfinished visits and reports NULL instead of zero when there are no samples. It is intentionally not a public view or browser RPC. The team's future admin page must establish an authorized aggregate-only interface and small-sample disclosure rules before exposing this result. Do not expose `app_visit` to browser roles.

## Rollout and operational dependencies

The migration `supabase/migrations/20261105032816_visit_metrics.sql` targets **provo-parking**, `rikekjksneoymybnehpo`; apply it before deploying the frontend and preserve existing rows. Run the local real-Postgres tests and inspect the production security advisor. Coordinate future timer and map changes against these hooks.

New visit opens are limited to 40 per forwarded address per ten-minute bucket. The database stores only a keyed, bucket-specific address digest in a private table, removing expired counters opportunistically. This is a coarse safeguard, not proof against distributed or spoofed requests; guest metrics remain untrusted. Each new opening removes up to 50 unfinished visits older than seven days. Cleanup is opportunistic: if no one opens the app, expired records remain until a later opening. Completed records remain to support the KR; account-linked records are removed when the account or linked session is deleted. Only the new visit records and counters are eligible for this cleanup; parking sessions and pre-existing data are never deleted by it.

Local verification uses `npm run check`. For real PostgreSQL/RLS tests, configure `P7_TEST_DATABASE_URL` to the explicitly named disposable local database `provo_parking_p7_test`; the test helper rejects remote hosts and other database names. `tests/visit-metrics-db.test.js` drops and rebuilds schemas in that disposable database, so never point it at real data. The tests exercise raw access denial, account ownership, guest capabilities, idempotent retry, latest matching, and the one-hour exclusion. Production checks must not create or alter another person’s parking session. Verify RPC availability and browser-role restrictions with a disposable, unfinished visit and confirm the published site.
